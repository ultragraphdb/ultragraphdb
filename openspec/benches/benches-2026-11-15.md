# Benchmarks, 2026-11-15: the baseline before the system group moves

Reads and writes through the three role binaries on the stage 5.7 cluster, taken before stage 5.8 moves the cluster's
books to storage (`openspec/changes/stage-5-8-system-group`, task 0.5). Stage 5.8's group 9 and stage 5.9 rerun this
record with `scripts/bench_cluster.sh` and compare against these tables. The record of 2026-11-09 holds writes alone, at
an older commit and on a setup this record corrects, so the two do not compare point by point.

## What ran

- **Commit:** `7d573798`, with the working tree's changes to `ultragraphdb_common_service` and
  `ultragraphdb_common_service_config` (the pinning of *What the setup corrects*) and to `client_bench` (its loading).
  The storage engine is the KV store, fjall.
- **Build:** `bazel build -c opt --platforms=@rules_rs//rs/platforms:aarch64-unknown-linux-gnu` of
  `//ultragraphdb/ultragraphdb_config`, `//ultragraphdb/ultragraphdb_frontend`, `//ultragraphdb/ultragraphdb_storage`,
  `//ultragraphdb/ultragraphdb_compute` and `//ultragraphdb_tool/ultragraphdb_tool_bench:client_bench`, copied from
  `$(bazel info output_path)/aarch64-unknown-linux-gnu-opt/bin` into the directory the machines mount at `/m7`.
- **Host:** macOS 27.2 on an Apple M3 Max, 16 CPUs, 128 GiB; Apple `container` 1.7.1. Each machine is a Linux VM, and
  `container` gives a machine one CPU more than `--cpus` asks for.

| Machine | Runs | CPUs | Memory | Image | Data |
|---|---|---|---|---|---|
| `ugdb-s` | storage alone | 6 | 8 GiB | `debian:trixie` | named volume at `/var/tmp/m7` |
| `ugdb-f` | the config service, the frontend, compute | 6 | 8 GiB | `debian:trixie` | named volume at `/var/tmp/m7` |
| `ugdb-c` | the clients | 4 | 4 GiB | `cgr.dev/chainguard/wolfi-base` | none |

```sh
M7=/path/holding/bin/keys   # mounted at /m7
container volume create ugdb-m7s; container volume create ugdb-m7f
container run -d --name ugdb-s --cpus 5 --memory 8g -v ugdb-m7s:/var/tmp/m7 \
  --mount type=bind,source=$M7,target=/m7 docker.io/library/debian:trixie sleep infinity
container run -d --name ugdb-f --cpus 5 --memory 8g -v ugdb-m7f:/var/tmp/m7 \
  --mount type=bind,source=$M7,target=/m7 docker.io/library/debian:trixie sleep infinity
container run -d --name ugdb-c --cpus 3 --memory 4g \
  --mount type=bind,source=$M7,target=/m7 cgr.dev/chainguard/wolfi-base:latest sleep infinity
```

- **A point:** `M7=… scripts/bench_cluster.sh <partitions> <op> <connections> [client_bench flags]`. The script writes
  the settings, and for each of three runs stops every process, empties both data directories, starts the config
  service, the frontend and compute on `ugdb-f` and storage on `ugdb-s` as user 65532 over TCP, waits until a
  one-second client run succeeds, and runs `client_bench` for 20 timed seconds: one process to 63 connections, two to
  255, four from 256, the connections split evenly. The settings are those of 2026-11-09 (`epoch_ms_min` 2,
  `epoch_ms_max` 10) with five partitions and, in every role's file, `[runtime] pin_cores = true` and `pin_skip = 1`.
  `PIN=0` leaves the `[runtime]` table out.
- **The keys** are 96 hexadecimal digits each with no newline: the client refuses a password that ends in one.
- **The operations.** `read`: a read-only transaction at snapshot level, Begin, one Read of one subject's statements
  drained to its end, Abort; each connection first writes 1,000 subjects. `span`: a read of a predicate holding one
  row in each partition. `scan`: a read of every `w` of the cluster. `direct`: a DirectWrite through a session of `R`
  new nodes, each with an edge to one of 1,000 hubs and a string. A connection has one request in flight.
- **Method:** three runs a point; the median with the range in parentheses. Requests a second are the processes' sum;
  the latencies are the median process's of the median run, from the call to its answer; the mean is weighted by
  requests. *Softirq* is the share of CPU 0 that each machine spent in network interrupts over six seconds of the
  timed part, clients / frontend's machine / storage, the median of the runs. No run refused a request or left one in
  doubt.

## What the setup corrects

Three things the first attempt at this record found, each root-caused before these tables were taken.

1. **`client_bench` loaded one connection at a time.** A read run's connections wrote their subjects one after
   another, so a run of 256 connections took five and a half minutes for its 20 timed seconds. They load together
   now, and the run takes 44 seconds with the same result.
2. **A partition's thread shared a CPU with the machine's network interrupts.** In each VM every network interrupt
   lands on CPU 0. Unpinned, whichever partition thread the scheduler left there was starved, and the reads of its
   keys, one in six, queued for 70 ms and more. `[runtime] pin_skip = 1` leaves CPU 0 to the interrupts.
3. **`pin_cores = true` bound every runtime of a role to one CPU.** The role's first thread bound itself to one CPU,
   and every thread it started could ask for that CPU alone. The first thread is bound to all the role's CPUs now, and
   each runtime to one of them. Storage with the setting on read 8,353 times a second at 256 clients before the fix.

| 256 clients, `read`, five partitions | Reads/s | p50 ms | p90 ms | p99 ms | Mean ms | Softirq |
|---|---|---|---|---|---|---|
| Unpinned (`PIN=0`) | 15,142 (14,379–15,475) | 2.47 | 71.12 | 93.94 | 16.88 | 62 / 96 / 75% |
| Pinned, CPU 0 left free | 25,297 (25,139–25,860) | 10.05 | 11.70 | 14.07 | 10.12 | 72 / 100 / 83% |

Pinned, 256 clients read 67% more a second, outside both spreads, and the p99 falls from 94 ms to 14 ms. The median
rises from 2.5 ms to 10 ms: unpinned, five reads in six met no queue and the sixth waited; pinned, every read shares
the one limit that is left.

- Reads stop growing near 25,000 a second, where CPU 0 of the frontend's machine spends all its time in network
  interrupts. No role's thread is the limit: at 256 clients the partitions' CPUs are half idle and the frontend's and
  compute's about a quarter idle.
- A read costs about thirteen packets on the frontend's network card and six round trips one after another: Begin and
  Read from the client, then three Scans from compute to the partition, for the dictionary's gate, the list and the
  terms. A partition answers a Scan in 38 µs on average while the Scan's round trip takes 2.6 ms. Whether a read can
  take one Scan and one frame is items 15 and 18 of `openspec/notes/backlog.md`.
- The relay between the frontend and compute, which stage 5.9 removes, costs 0.27 ms of a read here and runs over
  loopback, so the merge by itself does not lift this limit.
- The KV store is not the limit of a read through the binaries. Stage 6.5's comparison of engines needs the
  in-process figures, or a setup whose network is not what saturates.

## What was not determined

- Each configuration of the root-cause work ran once or twice; only the tables above ran three times.
- The capacity of the interrupt CPU was never varied: the VMs refuse changes to interrupt affinity, receive packet
  steering and threaded NAPI.
- Whether a physical Linux machine with a multi-queue network card shows the starved thread, and where reads stop
  there, is item 14 of `openspec/notes/backlog.md`.
- With 1,024 clients the reads' limit is not the interrupt CPU of the frontend's machine (74%); what it is was not
  measured.
- The frontend and compute take the pinning code that storage takes; their bindings were read in the logs, and no
  measurement isolates what pinning buys in each.
