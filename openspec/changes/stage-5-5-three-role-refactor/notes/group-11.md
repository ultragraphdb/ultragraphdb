# Group 11: supervisor, images and the rest of the binaries

## 11.1–11.3 The supervisor, the exit codes and the fallback

**The first failing run.** The scenarios were written first and bound against a supervisor of one `unimplemented!()`: `ultragraphdb_supervisor_tests:bdd`, 14 scenarios, 2 runs of 172 s each, each scenario failing as `127.0.0.1:18081/ready never answered` or by the exit it expected. Phase 3 added four for the corner cases enumerated afterwards: a role stopping cleanly by itself, a signal during the start, a stray variable and a binary not there. Those four ran first against the implementation.

**How it is started.** `ultragraphdb_supervisor --config <file>`, the config service's own settings file, passed on to it unchanged. That file names the address, the keys and the central file, so the supervisor adds no setting. Each shipped profile takes one, `profiles/dev.toml` and `profiles/dev-net.toml`, beside its folder and out of the validator's stray-file warning. They name `targets_file` under `/etc/ultragraphdb/profiles/`, where task 11.4's image must lay them. The binaries stand beside the supervisor. It asks the service in clear text and refuses a file asking for TLS, naming `config.plaintext`, since it runs inside one container.

**What it asks the service.** Once the service's `/ready` answers, `/v1/targets` names the one target with an active revision, and the admin key's `/download` gives its files, whose merged settings say each role's observability address. So an edit made through the API is what the next start waits on, and the supervisor never reads the central file. A store holding several active targets, or none, is refused by name, since the instances' addresses are per target and one container runs one. The store keeps what it once seeded, so the refusal says editing the central file changes nothing, and gives the way out: `ultragraphdb_config --config <file>` alone, then `DELETE /v1/targets/<name>` or `PUT /v1/targets/<name>/active` under the admin key, or an empty data directory. The scenarios follow that way out to readiness.

**Waiting.** A wait for a role has no deadline of its own: a role's join deadline ends a role that cannot get there, and a recovery takes the time it takes. Every 10 s the log says what is awaited. A wait ends at a signal or at any process ending. A role told to stop has 70 s, past the 60 s it gives itself, then is killed and reported as 137; no test waits that out.

**Stopping.** Each process has a process group of its own, so a terminal's Ctrl-C reaches the supervisor alone and the order holds. For the same reason a closed terminal's SIGHUP reaches it alone, and dying of that would leave the roles running, so SIGHUP and SIGQUIT stop everything as SIGTERM does, `nohup` included, since a handler replaces an ignored signal. SIGKILL and an OOM kill of the supervisor orphan nothing: it sets `ULTRAGRAPHDB_PARENT_PID` to its own process for everything it starts, the config service included, and each stops as on SIGTERM once that process is no longer its parent. As PID 1 in the image it names process 1, which stays a role's parent until its death ends the namespace. The help says so. The signal that arrived is what the roles receive, and SIGTERM when a failure stops them. A role a forwarded signal kills, its handler not yet installed, stopped as asked. A role exiting 0 unasked ends the container with 0, since nothing failed. The config service stops last. `kill(2)` comes through `rustix`, since the image has no `kill` tool and `Child::kill` sends only SIGKILL.

**What a frontend's stop finishes.** `OpenRequests` counts every frame a connection has taken until what it asks is on the wire, past the flush, and refuses a request arriving once the service stops with code 17. `finish_open` cancels the accept tasks, which closes the listeners, then waits on the count for up to 50 s, inside the 60 s a role has, so a client reading no answer costs a warning and no failed stop. Only the frontend counts today. A request answered by `Answer::Open` and `next_push` is not counted, because a Subscribe is one and never ends: 9.5.5's client streams must count themselves, and 9.5.4's compute must take the same stop when it hosts a read.

**Secrets.** The two keys are drawn as the spec says. The spec leaves the role secret silent, and a container starting with no configuration has no other source for it, so the supervisor draws that too and the profiles name `/data/config/role.secret` in place of `/run/secrets/ultragraphdb_role_secret`, which nothing in the container provides. Each is 32 random bytes as 64 hexadecimal digits at mode 0600, kept where it stands, written under `<file>.drawing`, synced and renamed, so a draw cut short leaves nothing a later start takes for the secret and that start writes over the temporary name.

**The layout.** `meta/`, `seq/` and `storage/p1/r1/`, as the spec reads: the frontend's logs were `metadata/` and `sequencer/`, and a partition's directory gained its replica. No cluster data exists to migrate. The profiles' sockets moved from `/run/ultragraphdb/` to the spec's `/run/ultragraph/`.

**Exit codes.** `RoleError::EXIT_CODES` is the one table, in each role's `--help` and the supervisor's, which adds 128 plus the signal. A panic on a partition's thread now counts: its channel ends without a word, which reads as code 70, where the loop used to pass over it.

**An invariant violation.** No partition checked an invariant a process test could reach. `deliver_closes` now holds that a close follows the last by one epoch, which every real frontend keeps since the sequencer closes in order and a subscriber too far behind is refused, not skipped. It returns `RoleError::software` directly and not through `invariant()`: the check reads what a peer sent, and a debug build's panic on a detached task would be swallowed. The other partitions stop through `stop_the_rest`, each flushing. `storage_tests`' `played_frontend.rs` delivers close 5 first.

**A lost dependency.** Compute dials the frontend and each partition the Members named at its readiness twice per `join_deadline_ms`, each dial limited to the time left, and exits 69 naming the address once one has not answered by the deadline. A held connection could not tell: a stopped peer or a lost host closes nothing, the protocol has no ping and a role connection no idle limit. A dial asks for a Welcome and a proof of the secret, which the kernel's backlog cannot give, at the cost of one SCRAM exchange at 4,096 iterations per peer per half deadline. A partition joining after readiness is not asked. 9.5.4's read connections left this watcher in place, and it is still compute's one check of a lost peer. `Carrier` sets `PROTOCOL.md` §11.4's TCP keepalive on every TCP connection.

**A storage thread's end.** A oneshot receiver gives its outcome once and then reads as a sender gone, so a look that heard a clean end made the wait after it report a silent thread and exit 70, about one stop in ten during a join. `CoreEnds` lets each receiver go once heard, and its `finish` waits for every thread, so a failure no longer ends the process under another partition's flush.

**io_uring.** The workspace's compio takes `polling` beside `io-uring`, which on Linux builds its fusion driver: it opens a ring to probe, and any refusal, Docker's seccomp included, gives the polling driver. So the fallback is compio's and the role's part is the log line, from `core_runtime`, one per runtime.

**What runs where.** Every scenario of the supervisor's, the exit codes' and "The data layout matches a node's" runs here on the shipped `dev` profile, paths and ports moved into the test's own, by the real binaries. `A failing role ends the container with its code` is real too: the test replaces storage's log with a file and asks it to load its revision, so its restart fails on the store with 74, while the frontend and compute run on. `A refused io_uring falls back` is the refusal itself on macOS, which has no io_uring; on Linux with io_uring allowed the same role says so, and only 11.4's Docker run proves the refusal there.

`features/role_binaries/images.feature`, tagged `@image`, holds four scenarios `tests/bdd.rs` leaves out, verbatim and unbound, for 11.4: "A role image holds its binary alone", "The development container uses Unix sockets" (its write and read also need 9.5.5), "The same frames cross TCP", "The seccomp profile enables io_uring". A socket's owner 65532 needs the image too: `listen` sets mode 0600, and the owner is whoever the process runs as.

**What 11.4 must lay in the image.** The binaries in one directory; the profiles under `/etc/ultragraphdb/profiles/`; `/run/ultragraph` and `/data` writable by 65532, since neither the supervisor nor `listen` creates a socket's directory. `listen` refuses a socket path it cannot bind with code 78, naming the directory or the file in the way and saying what to do; a TCP port in use stays 69.

**The Linux path has not run.** Everything above ran on macOS. The supervisor and storage were built for `aarch64-unknown-linux-gnu` under Bazel, and `ultragraphdb_transactions_log` checked for `x86_64-unknown-linux-gnu`, so the fusion driver compiles; it has not been run.

Results under Bazel: `ultragraphdb_supervisor_tests:bdd` 24 scenarios, 48 steps, three runs in a row; `ultragraphdb_compute_tests:bdd` 8 scenarios; `ultragraphdb_frontend_tests`, `_config_tests`, `ultragraphdb_tests`, `ultragraphdb_common_service`, `ultragraphdb_error_role` and `ultragraphdb_common_frontend` green. `ultragraphdb_storage_tests:bdd` 57 scenarios, "Storage flushes on shutdown" and "Storage is not ready before recovery" among them, over the `p<n>/r1` directory. `make test` is the owner's gate, once 9.5.3b returns. Mutation testing runs once, in 11.5.

## 11.4 The images, and the Linux run

**What is built.** Each role's package declares `load` beside its `<role>_multiarch`, tag and `push`, the config service's too, and the glibc base a `load` the scenarios compare layers against. `glibc_multiarch_img` and `scratch_multiarch_img` now lay the binary alone, `include_runfiles = False`: the runfiles tree was a second copy of the binary and its repo mapping. `//ultragraphdb/ultragraphdb_supervisor:development_multiarch` is the development image: the supervisor, the config service and the three roles at `/`, the shipped profiles under `/etc/ultragraphdb/profiles/`, and `/data` and `/run/ultragraph` owned by 65532 at 0700, a tar of `tar.bzl` mtree lines, since a rules_img layer sets no directory's owner. It runs `--config /etc/ultragraphdb/profiles/dev.toml` as 65532, with `development_tag`, `push` and `development_load`. `bazel/oci_images/seccomp/ultragraphdb.json` is Docker's default, moby/profiles `seccomp/v0.3.0`, with one rule after its first allowing the three io_uring calls.

**A write needs a principal.** The `dev` profiles named no bootstrap secret, so no client could log in to the development container. Both `frontend.toml` files now name `metadata.bootstrap_secret_file = "/data/config/bootstrap.secret"`, and the supervisor draws it as it draws the role secret, where nothing is there; an operator reads it with `docker cp`.

**The TCP scenario's text.** "the frames each role exchanges are byte-identical to the Unix-socket run's" cannot hold of two runs: a Join carries its role address, SCRAM its nonces, a Result its epoch. `PROTOCOL.md` §11.12's "The frames are the same on both carriers" is the encoding, and stands. The scenario now reads "and the read's rows are byte-identical to the Unix-socket run's", in the spec and the feature.

**The scenarios in Docker.** `image_bdd` binds `images.feature` and `io_uring.feature`, now tagged `@docker`, from the same `tests/bdd.rs`, its steps in `tests/images.rs`: each image loaded by its load target for the daemon's platform, every Docker command bounded at 120 s, each container and network removed when a scenario ends, ports the daemon picks. The storage image adds one layer and one file to the base, its binary; the index names linux/amd64 and linux/arm64. The development image's roles meet at the three sockets its profile names, which `docker diff` lists, and a DirectWrite and a read through the published endpoint return `<b>`. Over TCP the config service's scratch image and the three role images run in four containers of one network on the `dev-net` profile, the loopback replaced by each container's name, and the read's rows equal the development container's. Under Docker's default profile every runtime logs the polling driver and serves the write and the read; under the shipped one every runtime logs io_uring. The first run failed two scenarios on the test's own expectation, a read's row holding a second, empty column; the second, 5 scenarios, 10 steps, passed, and `bdd`, 24 scenarios, still passes. With no daemon `image_bdd` prints that it skipped and exits 0, as scrith's container tests do.

**On Linux.** OrbStack's kernel 7.2.12, linux/arm64. `ultragraphdb_supervisor_tests:bdd`, `ultragraphdb_storage_tests:bdd` and `ultragraphdb_frontend_tests:bdd` were built for `aarch64-unknown-linux-gnu` and run in `cgr.dev/chainguard/wolfi-base` as 65532, the output base and the tree mounted read-only, `TEST_TMPDIR` on a volume: a tmpfs of 6 GB ran out under storage's 83 stores, which said so with code 74, `No space left on device`. **A port a killed role leaves held.** A killed process is reaped before the kernel tears down the io_uring ring it ran on, and an accept in flight on that ring holds its listener until then. Measured on Linux 7.2 (OrbStack, arm64, 12 CPUs), as 65532 in a Wolfi container under the shipped seccomp profile, from the reaping to the first bind that succeeds, polling each 200 µs: the config service with its accept in flight, killed 1,000 times idle, had its port held at the first bind 603 times, median 3.3 ms, p99 7.1 ms, worst 8.3 ms; killed 500 times under 16 clients half reading and half writing through its log, 12 spinning threads and 4 threads syncing to disk, 385 times, median 2.9 ms, p99 5.2 ms, worst 14.2 ms; killed 300 times under 64 clients, 24 spinning threads and 8 syncing, 201 times, median 2.2 ms, p99 5.0 ms, worst 9.2 ms. `until_ports_free`, timed over storage's and frontend's suites in three runs, 300 kills of whole scenarios, two of the runs beside that load, waited a median of 2.7 ms and at worst 9.3 ms. Under Docker's default profile, on the polling driver, 300 kills held the port never, worst 0.3 ms; after a SIGTERM it is free at once. So a role and the config service retry a TCP bind refused with `EADDRINUSE` every 50 ms for up to 5 s, over 350 times the worst measured, a margin kept wide because the supervisor restarts nothing, logging each retry with the address, then exit 69 naming it and saying to stop what holds it. Any other bind error ends the start at once, and a Unix socket's path takes no retry: a socket left behind is replaced, and a file in the way stays in the way. `bind_tcp` in `ultragraphdb_common_service` is the one place: `listen`, the observability listener and compute's `CoreListener` all bind through it, and the config service through `listen`. A start also reaches its bind late: the config service opens its log first, so 500 starts at the moment of the reaping lost no port on the binary without the retry; the frontend reaches its bind sooner, which is where the 69 was seen. Storage's and frontend's suites keep their `before` hook, `until_ports_free`, because a step may dial a role's address once `/health` answers, and a role retrying that bind is not yet listening: with the hook out, under the shipped profile, storage's suite passed 3 of 3 runs of 84 scenarios and frontend's 2 of 3 of 19, the third failing "Epoch closes reach storage in order" with a refused connection at that dial. Compute's suite keeps its clusters up for the whole run and takes no such wait.

**After the four tracks' review.** The supervisor draws the bootstrap administrator's password before the cluster's first start alone, while the frontend's data directory holds no `meta/`: a password the operator removed after reading it stays removed. The development scenario asserts the image's user, 65532, and `/run/ultragraph` at 0700 owned by 65532:65532, read from the archive `docker cp` makes of it, which carries no socket; each socket's 0600 is asserted on the host by `ultragraphdb_tests`. **After the end-of-group review.** The supervisor sends no signal to a process whose status it has read, since a reaped process's ID may be another's. It refuses with code 78 a target whose instances name more than one `role_secret_file`, naming two of them, before it draws any secret: "Two role secret files in one container are refused", new in the role-binaries spec. A signal that finds no process is logged as a warning, which "A failing role ends the container with its code" asserts is absent, and which it saw with the check taken out. `SECURITY.md` states that the development container's processes can all read both keys, and the role-binaries spec that the seccomp profile ships in the repository, each what the image does; keeping the key from the roles' uid and publishing the profile beside the images remain the owner's to ask for.

**After the wave's three decisions.** The config service and the supervisor honour `ULTRAGRAPHDB_PARENT_PID` as the roles do, through `stop_with_parent`, and a supervisor at PID 1 named a parent stops at once, as any process naming one that is not its parent does. The supervisor sets the variable to its own process for everything it starts and logs `parent=` beside each `pid=`; "A killed supervisor orphans no role" kills it with SIGKILL and waits for all four processes to end, each logging its own stop, with their ports free, and it read `["config", "frontend", "storage", "compute"] still ran 20 s after the supervisor was killed` before. "A role whose parent is PID 1 runs on", in Docker, confirms what a role does with process 1 named: its parent stays 1, no role stops, and a write and a read succeed; it failed with the log's `parent=` taken out. A role link's dial is bounded at `transaction_ms`, 10 s, by `RoleLinks::with_dial_ms`, which the frontend sets from its limits: past the bound the link fails as a closed one does and a warning names the address and the bound, which closes what group 9 left. "A role connection's dial past its bound closes it" holds a read over a peer that accepts and says nothing and failed with `no frame came` before. A read-write transaction's own limit runs out at the same moment, so a Write over such a dial is answered with code 4 or 17, whichever timer fires first. What is left: a signal during a bind's retries waits for them, up to 5 s; the measurement ran in one VM, and `until_ports_free` could leave the suites once their steps wait on a role's address rather than `/health`.

**A refusal a client never read.** `ultragraphdb_config_tests:bdd` failed "A request's declared body is larger than the bound" with `nothing answers at http://127.0.0.1:17090: Broken pipe (os error 32)` where it wants 413. Counted over 100 runs of that scenario, before any change: 4 on Linux under the shipped profile, on io_uring; 0 under Docker's default profile, on the polling driver; 3 on macOS through Bazel, where `flaky_test_attempts=2` in `.bazelrc` passes such a run on its retry, and the summary's "103 runs" was the one sign. The cause is the one the owner read, in two parts. The service answered from the head, shut its sending side and closed over the bytes it had not read, so the kernel sent a reset: `OutRsts` in `/proc/net/snmp` counts 1 across the scenario on either driver and 0 across the one asking for `/health`. A client still writing then fails, EPIPE because its socket had already seen the FIN, which is a race on whether its 512 KiB had reached the kernel: a client writing again after the refusal failed on each run, on both drivers and on macOS. And `HttpClient` returned that failure without reading the 413 waiting in its own socket. `serve_http` now follows any refusal given before a body is whole, 400, 408, 413, 431 or 501, by shutting its sending side, as it did, and reading what still arrives into one buffer it discards, until the peer ends, `HttpLimits::DRAIN_MAX` (16 MiB) has passed or the request's time has passed again. So a refused connection holds a task for three times the request's time at most, and no more memory than that buffer. A role's observability and admin listeners and the config service all answer through `serve_http`, so each takes it. A request read whole gets no drain: its refusal, 401 or 403, leaves nothing unread unless the peer sent more than it declared. `HttpClient` now keeps a failed write's error and reads on, telling it only when no reply follows. "A refusal reaches a client still sending", new in the config-service spec, writes on through a raw socket after reading the refusal; it failed with `write 0 after the refusal: Broken pipe` before, and four tests of `serve_http` failed with the drain taken out. After: the config suite passed 10 of 10 runs on each driver, 36 scenarios, and the two scenarios 100 of 100 on each; on macOS through Bazel, retries off, the suite passed and the two scenarios 100 of 100. What is left: past the 16 MiB a TLS client still reads no refusal, since `CompioTlsStream::read` writes the records it owes before it reads and returns that write's failure. Measured with a 32 MiB body, in clear text the reply is read and over TLS the error is `Broken pipe`. No caller sends such a body: `HttpClient`'s callers send no body at all.

**`/health` says a role can be reached.** A role's `/health` answers once it holds its settings and has bound every listener it serves from its start, and 503 before: `Readiness` holds a listening flag beside readiness, which the frontend starts without (`Readiness::binding`) and sets once its role and client addresses are bound, and every other role starts with. So the supervisor and a test may dial a frontend once its `/health` answers, and "The frontend's /health answers once its listeners are bound" failed before it, answering 200 while the role address was held. Storage binds its partitions' addresses once they have recovered, with `/ready`, so its `/health` answers while it recovers and a peer dialling it meanwhile is refused at once, which the owner chose over binding before the replay.

**A storage start reads its catalog versions as it joins.** The read of the frontend's catalog versions at a start goes through `retry_until`, as the placement and the join do: a frontend not there yet or stopping under the start is asked again until the join deadline, and a stop ends the start cleanly. "A signal during the start stops what was started" failed on Linux on both drivers before it, storage exiting 69 when the supervisor stopped the frontend first. A tenant's versions end at the group's code 7 alone, so a connection lost part way fails the read, where it used to end it as though no version were left and replay against an incomplete set; no test plays a connection lost in the middle of that read, which 9.6's pass judges. The played frontends of the storage and compute suites answer a Catalog request with code 7, as a frontend holding no version does.
