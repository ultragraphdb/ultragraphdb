# PROTOCOL.md and SECURITY.md review (task 0.3)

On 2026-11-02 a sub-agent drafted task 0.3's update of `../../../../specification/PROTOCOL.md` and `SECURITY.md`. An
adversarial review (three reviewers by dimension, each finding checked by a skeptic) confirmed the defects below in
that draft, which stays uncommitted in the working tree. The placement decision P24, taken afterwards, settles several
of them and changes others; the fix pass of task 0.3 starts from the change's specs as they now stand, then works
through this list. A finding P24 makes moot is closed by saying so.

Settled since the review, and to be written into PROTOCOL.md:

- Statements reach clients by their quad when they hold no statement ID, and by their reifier IRI when they hold one;
  a Commit result names a node by its IRI or skolem IRI. No system ID crosses to a client.
- Level, session token and deadline are named on Begin. Read-write transactions read their partition's latest state.
- A Drop or delete by pattern reaching several partitions is cross-partition, refused in this stage.
- A request before authentication is refused and the connection stays open (client-endpoint spec); the frontend
  always requires authentication (no `auth` 0 mode).
- Catalog versions take effect at `c + 2`, assigned by the sequencer at the close of `c + 1` and announced with it.
- Registration (get-or-create at the home), referrer sets, reverse fan-out reads, close requests and session
  evictions carried with closes are role commands; resume keys hold terms as text, checksummed.

## Confirmed defects (41)

- **B1** (critical, §6.3 Commit (result layout), 11.6): The Commit reply's 16-byte result still carries a 64-bit node UID. Under the new identity model a node is a 128-bit system ID, which cannot fit the field, and the specs forbid any system ID in a reply to a client.
  Fix: Name the found or created node by text rather than ID. For example, give each result a term-table or string index, or give the Commit reply a string list holding the node's IRI or skolem IRI. Then redefine the 16-byte result (or its size), §11.6's wording and §12.2 section 9 to match.
- **B2** (critical, §9.1 Result (section 7), 4.6 change records 4, 6, 7): Result batches still return each row's statement ID as a u64, and Write still names a statement by two u32 halves. Statements are now 128-bit system IDs of type `Statement` (prefix 2), which neither width can hold. Returning them would also put system IDs in a result batch.
  Fix: Keep the Read, Execute and ComputeRead `flags` bit 0, because quad-reads requires statement IDs on request. Replace the raw ID with an opaque statement handle of stated width. The server alone encodes and decodes it, in the same way §11.8 treats resume keys (for example, checksummed so a changed byte is refused). Redefine §9.1 section 7 as handles of that width per row. Change §4.6 kind 4, and kinds 6/7 with bit 0 clear, to carry the handle: as handle bytes in a section, or as the right number of u32 args. Update §4.6 step 8's arg counts and step 9's 'ID halves take any value' together. Record the tension between quad-reads and system-identity for the user, so they can confirm that an opaque handle satisfies both.
- **B3** (major, §12.2 Write-set record (fixed part)): The write-set record's fixed part still holds `session` as a u64. The 16-byte session that Commit and Drop now carry cannot be recorded, so a partition cannot rebuild its session table on recovery.
  Fix: Widen `session` to 16 bytes. The fixed part becomes namespace 0–7, read_version 8–15, session 16–31, request 32–39, principal 40–47, so F = 48 (still a multiple of 8). Update "40-byte fixed part" in §12.2 and "the write-set record has `F = 40`" in §4.1. Remove "a session's registration (request 0)" from the recovery paragraph.
- **B4** (major, §12.2 operation record): A drop operation's `argument` is still a u64 naming the dropped predicate's or graph's UID. Predicates and graphs are IRIs, which are now 128-bit `Resource` system IDs, so the ID does not fit.
  Fix: Grow the operation to 24 bytes: operation u16 at 0, zero 2–7, a 16-byte argument at 8–23 holding a system ID for operations 1 and 4 and the record number in its low 8 bytes (or a separate field) for 2 and 3. Update section 10's `SectionLength` rule ("empty or one operation") and the zero-byte checks.
- **B5** (major, §6.5 Drop, 13.11 Recall, 11.5): Drop's reply has no session token, but §11.5 says every partition's table stores the token with each committed request. Recall answers "a Commit frame whose command header and body are the stored reply's byte for byte", which cannot reproduce a stored Drop reply: Drop's header puts `kind` at 0, `namespace` at 8, `session` at 16–31, `request` at 32 and `commit_version` at 40, and its sections are a term table. Commit puts `session` at 0, `request` at 16, `commit_version` at 24, `token` at 32 and results in section 0.
  Fix: First state how a Drop is routed and committed across partitions in §11.12 and §6.5: one round per partition, or one coordinating partition. Then define what each partition's session table records for it. Then either give Drop's header a token field (24 bytes at offset 48, unused 72–127) with a rule naming the partition and position it denotes, and let Recall answer with the stored reply's own command (Commit or Drop), updating §3's "Commit, or Error". Or exclude Drops from session tables and Recall, and remove 'and Drops' from §11.5's counter rule, accepting that a lost Drop reply has an unknown outcome.
- **B7** (minor, §9.4 code 26 detail): Code 26's detail packs a 24-bit bucket into bits 0–23 and a 32-bit partition into bits 32–63. Bits 24–31 are not stated as zero, so the u64 has more than one encoding. The packing does fit: 24 + 8 unused + 32 = 64.
  Fix: Add "bits 24–31 zero" to the detail. The receiving role may refuse otherwise.
- **B8** (minor, §13.2 Members): Members' order is enforced ("the member after the one before in the order above"), but with two or more compute processes every compute member has kind 2 and partition 0. The order among them is undefined, so it is unclear whether a second compute member is "after" the first, and the one-encoding claim in §4.7 fails.
  Fix: Order compute members by `address` index (equivalently, by address text, since addresses are interned in member order), or state that exactly one compute process joins in this stage and refuse a second.
- **F1** (critical, §PROTOCOL.md §4.6 (kinds 4, 6, 7), §6.3 result layout, §11.6, §7.1/§8.2 flags bit 0, §9.1 section 7, §13.12 flags): System IDs still cross to and from clients. Result batches return statement IDs, Write takes statement IDs from the client, and Commit results return a node's ID. That contradicts system-identity "System IDs never leave the database" ("No reply, result batch, error, cursor, resume key or IRI sent to a client SHALL contain a system ID") and the document's own §1 row. The fields are also 64 bits wide, so they cannot hold the 128-bit system ID that names a statement or entity (system-identity: "Every entity and every statement SHALL be named ... by a 128-bit system ID").
  Fix: Settle the spec conflict first: either statement IDs never reach clients, or a client-facing statement handle is defined that is not a system ID (an opaque token checksummed like resume keys, or a triple term). Then replace the u64 statement-ID column, the 2×u32 ID args of change kinds 4/6/7, and Commit's `uid` result with that handle or with the node's IRI/skolem IRI through the term table. Commit's `uid` can name the node by a result term.
- **F2** (major, §PROTOCOL.md §6.2 Begin, §7.1 Read, §8.2 Execute, §11.11): The read level and the session token are carried by Begin, once per transaction, not by the read request. The specs require each read request to name its level and carry the token, and they put the timeout on the request's deadline. Read and Execute gained no `level`, `token` or deadline field.
  Fix: Either add `level`, `token` and a deadline to Read/Execute (and to ComputeRead's derivation), or amend wire-protocol and quad-reads to say the transaction's Begin names the level and carries the token for every read in it. Leaving both in place keeps the document out of conformance.
- **F3** (major, §PROTOCOL.md §11.1 step 6, §9.4 code 20): A data request before authentication closes the connection. The client-endpoint spec says the connection stays open for authentication.
  Fix: Refuse a pre-authentication request with code 20 on the request's stream and keep the connection open. Close it only when the authentication timeout expires. Update the code 20 row to match.
- **F4** (major, §PROTOCOL.md §11.5, §13.11 Recall): The rule for combining Recall answers into a reply to an unroutable retry breaks exactly-once. Recall has no answer for a request still in the commit step: the partition answers 18 because its table does not hold the request yet, so the frontend tells the client NotCommitted and the client runs the transaction again while the original commits. The frontend's rule also covers only two outcomes, stored reply and "none": a partition that answers 12 (it evicted the session, so the outcome is unknown) or 13 still yields 18, which turns an unknown outcome into "not committed". Separately, nothing says how a partition tells "evicted" (12) from "never seen" (18) once the session has left its table.
  Fix: Drop the proposed Recall answer of 14: the frontend already answers 14 from its own in-flight tracking. Define the combination in §11.5: a stored reply wins; otherwise any 12 gives 12 (outcome unknown); any 13 gives 13 (or the stored outcome); 18 only when every partition answers 18. In §13.11, say how a partition remembers an evicted session, for example an eviction watermark or a bounded set of evicted identities, so it can answer 12 rather than 18.
- **F5** (major, §PROTOCOL.md §11.11, §11.12 Reads, §13.12 ComputeRead): When a read-write transaction's read reaches a second partition, compute answers code 23 on the read's stream. Nothing aborts the transaction at its storage partition: the Bind stream gets no Abort or Cancel, and §11.2 does not say a read's Error ends the transaction. A following Commit is relayed and commits. That contradicts partitions "A transaction reaching a second partition aborts ... and holds nothing" and makes that scenario fail as written.
  Fix: State that on code 23 from compute the frontend cancels the Bind stream (aborting the transaction at storage), ends the client's transaction, and answers its next request on the transaction's stream with code 23.
- **F6** (major, §PROTOCOL.md §11.12 Writes, §9.4 codes 23/26): The document never says which key's bucket makes a partition answer 26 or 23. Per term-dictionary, a new object IRI's dictionary entry and sequence belong to the partition owning the object's bucket. Read literally, "a key outside its bucket ranges" therefore refuses a write of <a> <knows> <b> whenever <b> hashes to another partition. Routing by subject bucket alone, as the spec requires, is not stated either.
  Fix: State that only a statement's subject bucket (and an entity's own bucket for entity-keyed writes) decides routing, 26 and 23. Say how an object IRI whose dictionary entry lives in another partition gets its ID inside a single-partition transaction, or have the spec state that such a write is a CrossPartition abort.
  Specified 2026-11-03 for statements named by their reifier: §11.12 Writes and transactions, "Aborts name their reason", check a delete or property change through a reifier against the subject the reifier resolves to, after execution, aborting with code 23 when another partition owns it.
- **F7** (major, §PROTOCOL.md §11.12 Writes, §13.10 Bind): The binding rule for a transaction whose first write names only new blank nodes is missing. Bind goes to "the partition its placement map gives that key's bucket", and a request-scoped blank-node label has no bucket until a partition mints its skolem IRI.
  Fix: Add: when the first request's subjects are all new blank nodes, the frontend binds to the next partition in round-robin order. That partition mints each node's bucket from its own ranges.
- **F8** (major, §PROTOCOL.md §6.5 Drop, §11.12 endpoint table): Drop has no path in the role topology and no session token. No role endpoint serves Drop, and a predicate, namespace or every-namespace drop reaches every partition. Even so the document says it "commits as a transaction does" through a session, with a reply "answered as a Commit is", and gives it no token field. That conflicts with transactions "A committed transaction's reply SHALL carry a session token", with single-partition transactions, and with the per-partition session tables.
  Fix: Specify how a Drop is executed across partitions in this stage (refused, or fanned out per partition with defined session and token semantics), add a `token` field or state why none applies, and list Drop in the relevant endpoint's served commands.
- **F9** (major, §PROTOCOL.md §13.7 Catalog, §13.4 EpochClose, §11.12): Nothing tells a partition that a new catalog version exists, and nothing creates one. Catalog is pull-only (version 0 means current). EpochClose carries no catalog change, and declarations (Write kinds 8–10) are relayed to the bound partition, not to the metadata group. A partition cannot know it must validate epoch-40 rounds against version 3, so the metadata-group scenarios cannot be tested through the protocol.
  Fix: Add a catalog-version announcement (for example a field in EpochClose naming the latest catalog version and its effective epoch per namespace, or a pushed Catalog on the Subscribe stream). Define where a declaration becomes a metadata-group version offer and the refusal that names both versions.
- **F10** (major, §PROTOCOL.md §9.4, §11.9): The connection bound and its limit error are not stated. No error code or procedure covers a connection beyond the frontend's bound, and no bound on pending requests per connection is given. Code 15 StreamLimit covers streams only.
  Fix: Add a connection limit to §11.9. Define its refusal: an Error on stream 0 in place of Welcome, with a code such as a new ConnectionLimit or code 15 with `detail` the limit, followed by the close. Pending requests need no separate bound, because `max_streams` bounds them. Say so explicitly in §11.9.
- **F11** (major, §PROTOCOL.md §11.8 Resume keys): A resume key is required to contain no system ID, and resume keys must be refused when used with another pattern. §11.8 states neither. It never forbids system IDs in the key, while the design has the key hold "the last key", a store key carrying system IDs. Its refusal rule only catches keys outside the pattern's key range or with a bad checksum, so a key from another pattern whose bytes fall inside this pattern's range (from (s,p,?) reused with (s,?,?)) is accepted.
  Fix: State that a resume key holds the pattern's hash, that the server refuses one whose pattern hash differs from the request's, and that the key's bytes contain no system ID (for example the last row as terms by text, or the last store key encrypted under a server key).
- **F12** (major, §PROTOCOL.md §11.1 step 6, §5.2 `auth` 0; SECURITY.md Stage 5.5 row): The document keeps the no-authentication mode (`auth` 0, anonymous principal on loopback) on the frontend. The specs require every connection to authenticate against a metadata-group principal, and a cluster with no principal to refuse every connection.
  Fix: Remove `auth` 0 from the frontend's client endpoint for this stage. Alternatively, get the specs amended to allow a loopback-only anonymous mode explicitly, saying how it fits with "a cluster with no principal SHALL refuse every connection".
- **F13** (major, §PROTOCOL.md §12.2 write-set record, recovery paragraph): The partition's durable session table is still recorded with a u64 `session` field, which cannot hold the 16-byte session identity. The record also still treats a session's registration as a partition write (request 0), while registration now lives in the metadata group. So the per-partition session table cannot survive a restart as §11.5 and the transactions spec require. Drop's `argument` likewise names predicates and graphs by u64 UIDs, which are 128-bit system IDs now.
  Fix: Widen `session` to 16 bytes, which grows the fixed part to 48. Remove the request-0 registration from partition recovery, since a partition records a session at its first commit there. Carry dropped predicate and graph IDs as 16-byte system IDs.
- **F14** (minor, §PROTOCOL.md §4.6 kind 8 / §11.12 (missing)): The required stage-5.5 refusal of vector-index declarations is not stated. A Write record of kind 8 with flag bit 5 is specified as valid, and no error code or message is given for refusing it in this stage.
  Fix: Add: in this stage a kind-8 record with bit 5 set is refused with code 7 (Refused), `detail` the record's index, the message naming the predicate and stage 8, and the catalog stays unchanged.
- **F15** (minor, §PROTOCOL.md §11.11): The document adds a read-only exception that the transactions and partitions specs do not contain: they say every transaction stays within one partition. quad-reads needs multi-partition reads, and every Read belongs to a transaction, so the specs contradict each other and the document settles it unilaterally.
  Fix: Get the specs amended to restrict the one-partition rule to read-write transactions, matching the document. Otherwise the unbound-subject quad-reads scenario cannot be reached.
- **F16** (minor, §PROTOCOL.md §4.4 step kind 5: 6): The refusal of a triple term nested too deep does not name the entry and depth that the wire-protocol scenario requires. Every neighbouring step lists its parameters; this one lists none.
  Fix: Write `TermTooDeep` (records' section, the entry, the depth, limit 32), matching the enum's fields.
- **F18** (minor, §PROTOCOL.md §11.12 endpoint table vs §13.8): The endpoint table says the frontend's role address serves Challenge and Verify to storage and compute. §13.8 says no frame carries them in this stage. As written, any process holding the role secret can use the frontend to check principals' SCRAM proofs, which goes beyond the spec's "verifying a principal's proof" by the endpoint authenticating a client.
  Fix: Remove Challenge and Verify from the frontend role address's served commands for this stage, or restrict the requester to a frontend role. Storage and compute would then get CommandNotServed for them.
- **F19** (minor, §PROTOCOL.md §11.12 Writes/Errors): The client's answer is undefined when the owner refuses the frontend's single resend with code 26 again. Code 26 is role-only and the frontend resends only once, so the client-endpoint scenario's failure path has no defined result.
  Fix: Say what the client receives after a second 26, for example code 17 Unavailable or a retryable code, on the transaction's stream.
- **IC-01** (major, §PROTOCOL.md §12.2 Write-set record, fixed part): The write-set record still stores the session as a u64, but a session is 16 bytes everywhere else in the edited document. A 128-bit session identity cannot be logged with the committed request, so the partition's session table cannot be rebuilt on replay.
  Fix: Widen `session` to 16 bytes and grow the fixed part to match (for example 48 bytes: namespace 0, read_version 8, session 16–31, request 32, principal 40). Update the "F = 40" statement in §4.1 and the "40-byte fixed part" in §12.2.
- **IC-02** (major, §PROTOCOL.md §12.2 Write-set record (sections 0–4, operations, recovery)): §12.2 is the stage-5 text unchanged. It specifies a physical record of store entries with catalog entries, written by "the commit step" into "the log". It has no catalog version, no derivation version and no system-ID quads. The change requires a logical record and forbids catalog keys in a partition. The swap/undo-a-build and recovery text still reads and writes "the store's catalog".
  Fix: Rewrite §12.2 to the logical record: quads with system IDs, new dictionary entries, the catalog version and the derivation version, with the refusal of an unknown derivation version. Remove the catalog-entries section and the build swap/undo operations that write catalog entries, or restate them against catalog versions in the metadata group that take effect at an epoch.
- **IC-03** (major, §PROTOCOL.md §12.2 operation `argument`): A drop operation's argument names the dropped predicate or graph by a u64 "UID". Predicates and graphs are IRIs, which carry 128-bit system IDs (prefix 1 `Resource`), so a u64 cannot hold the ID. "UID" is the stage-5 64-bit Dgraph term.
  Fix: Make the operation carry a 16-byte system ID for predicate and graph drops: grow the operation from 16 to 24 bytes, or move the ID into a section. Use "system ID" in place of "UID".
- **IC-04** (major, §PROTOCOL.md §6.3 Commit result `uid`; §11.6; §12.2 section 9): Commit replies give the client a node's internal ID. This contradicts §1, §10 and the spec rule that no system ID reaches a client. The field is also u64, while node IDs are 128-bit.
  Fix: Have insert-if-absent and upsert-and-link return the node by its IRI or skolem IRI, for example as a term-table entry like OperationFailed's value, and keep the 8-byte slot for counter add's value alone. Update §6.3, §11.6, §12.2 section 9 and the result layout's 16-byte size.
- **IC-05** (major, §PROTOCOL.md §4.6 change kinds 4, 6, 7; §7.1 and §8.2 `flags` bit 0; §9.1 section 7): Clients still receive statement IDs as u64s and send them back as two u32 halves. §1 defines a statement's ID as a 128-bit system ID that crosses only between roles, and quad-storage makes a statement ID a system ID of the `Statement` type. The width is wrong (64 bits against 128), and it breaks the no-system-ID-to-clients rule.
  Fix: Decide the client-facing statement handle (an opaque, checksummed token like a resume key, or a 128-bit value if statement IDs are explicitly excepted) and state it in §1. Then resize §9.1 section 7, the §9.1 order check ("8 bytes per row") and the args of §4.6 kinds 4, 6 and 7 to that handle. Flag the conflict between the system-identity spec and the quad-reads spec ("statement IDs SHALL be returned only when the read asks for them") to the user.
- **IC-06** (major, §PROTOCOL.md §6.5 Drop; §11.12 What each endpoint serves; §12.2 drop operations): Drop has no route in the three-role layout, and its text still assumes one commit step and a catalog kept in the store. (1) No storage endpoint serves Drop. (2) A predicate, namespace or all-namespace drop spans every partition, yet §6.5 says one commit step decides it in one round. (3) Namespace drops "write the initial catalog" into the store, which conflicts with the metadata group holding the catalog. (4) Drop's reply is "answered as a Commit is", yet its header has no `token`, while §11.5 says a session's stored reply includes the token.
  Fix: Specify how the frontend executes each drop kind across partitions: which role command, which partitions, and what commit version and token the reply carries. Add a `token` to Drop's reply, or state why it has none. Move catalog effects to new catalog versions in the metadata group. Add the command to the §11.12 endpoint table.
- **IC-07** (major, §PROTOCOL.md §3 (519, 520), §11.12 endpoint table, §13.8): Three places disagree on who sends Challenge and Verify. §3 says the client-authenticating endpoint sends them to the metadata group's host. §11.12 says storage and compute request them at the frontend's role address. §13.8 says no frame is sent in this stage because the frontend asks itself. Storage and compute authenticate no client.
  Fix: In §11.12, list Challenge and Verify as requested by a frontend (in stage 8) and never by storage or compute. Either drop them from the frontend role address's served set in this stage or keep them as served for stage 8, consistently with §13.8.
- **IC-08** (major, §PROTOCOL.md §2.5 step 3 (CommandNotServed) vs §11.12 endpoint table): The CommandNotServed rule applies to "a connection's receiver", which includes the side that dialled. §11.12 lists only the requests each listening endpoint serves. Read literally, a role receiving replies on a connection it opened (Welcome, Error, EpochClose, Members/Lease/Placement replies, Entries, Result, relayed Commit replies) would refuse them as CommandNotServed.
  Fix: Restrict step 3 to the accepting side's receiver for requests. Alternatively, state per endpoint which commands the dialling side accepts: replies of the commands it sent, Welcome, Authenticate, Error, EpochClose on a Subscribe stream, and Result/Entries on read streams.
- **IC-09** (minor, §SECURITY.md Sessions, statements and the log; PROTOCOL.md §12.2 `principal`): The edited SECURITY.md says security-catalog changes go only through metadata-group commands. The same file, and PROTOCOL.md §12.2, still say a partition's write-set record names the administrator of each security change.
  Fix: Remove "the administrator of a security change" from §12.2 and SECURITY.md, and state that the metadata group's command records the administrator.
- **IC-10** (minor, §SECURITY.md The security catalog and revocation; Audit): Revocation and audit text still describes stage-5 behaviour: one commit-version order and one write-ahead log that every write enters. Security changes are now metadata-group commands, ordered by group log position rather than by a partition commit version, and partitions keep separate logs.
  Fix: Restate the security epoch against the metadata group's ordering (for example, the epoch from which the change applies, as catalog versions do). Say that security changes are in the metadata group's log.
- **IC-12** (minor, §PROTOCOL.md §9.4 code 13 vs §11.5 and §13.11): Code 13 has two triggers. The error table says it covers a number that is not above the last, which includes equal. §11.5 and §13.11 raise it only for a number below the last, because an equal number is a retry answered with the stored reply.
  Fix: Change the code 13 meaning to "below the session's last request number in the partition it reaches".
- **IC-13** (minor, §PROTOCOL.md §11.2 request table): A stage-5 leftover still calls the session a number, while it is a 16-byte random identity.
  Fix: "Register with the session's identity, or Error; the stream ends".
- **IC-14** (minor, §PROTOCOL.md §12.2 recovery paragraph): Recovery still replays session registrations from the partition log. Registrations live in the metadata group, and a partition records a session only at its first commit.
  Fix: Drop "a session's registration (request 0) or"; replay writes the committed request and its stored reply into the partition's session table.
- **IC-15** (minor, §PROTOCOL.md §8.3 Describe section 5 (and §11.7 schema id)): Declaration order, and so the schema id the client hashes, is defined by "UIDs". That is the stage-5 64-bit term, and under the change these are 128-bit system IDs whose order depends on bucket hashes that are never sent to a client.
  Fix: Replace "the order of their UIDs" in both places in §8.3 with a defined order: either the declared IRIs' system IDs as §1 defines them, or the declared IRI's UTF-8 bytes. Check that the golden describe_reply.frame and its schema id 0xFE70341D112B65A9 still match the chosen order.
- **IC-17** (minor, §PROTOCOL.md §11.9 Limits): `max_write_set` is still bounded by "the server's log" and announced by "that server". The Welcome comes from the frontend, which hosts no partition log, and each partition has its own log on its own drive.
  Fix: State that the frontend announces at most the smallest per-record bound among the logs of the partitions it routes to: 261,328 when any partition's log runs on a drive with power-loss protection.

  Fix: Update design.md's citation to SECURITY.md *Where it is built*, Stage 8.

## Unverified findings on the wave-3 revision (2026-11-02)

A check of the revised PROTOCOL.md and SECURITY.md was stopped before it finished, by the user's choice, so that
verification moves into group 8's tests. What its reviewers had found is listed here for group 8 to confirm against
the code it writes; a skeptic's verdict is noted where one was reached.

- **BL-1** (major, §6.3 Commit (5) / 11.13 Declarations, *Its epoch*) — skeptic: confirmed: A declaration transaction's Commit reply cannot pass Commit's own reply rule. 11.13 requires the token to be zero. 6.3 requires every reply token's epoch to equal commit_version >> 22, and that value is never 0 here.
  Fix: Change §6.3's reply rule to: "in a reply, zero for a commit that reached no partition (a declaration transaction, section 11.13), else a token whose `epoch` is `commit_version >> 22`". The alternative is to give declaration commits a token, but the token has no partition or position to name.
- **BL-2** (major, §13.15 Reference (526), Order line) — skeptic: confirmed: The rule tying `entity` to `iri` is applied to replies as well as requests. Every accepted reply to a registration that named its entity by IRI fails it.
  Fix: Move the rule "`entity` all zero exactly when `iri` is not `ABSENT`" under "in a request" (and into refused replies, which echo the request). In a reply, require `entity` to be a valid system ID for outcome 0 whatever `iri` holds.
- **BL-3** (major, §12.2 Write-set record (kind 2, registration item) vs 13.15 Reference) — skeptic: confirmed: No write-set record can log a group-less registration: the get-or-create of a predicate's or graph's ID, or the frontend's unique-predicate lookup. 13.15 says these registrations are made durable in a round of the home's log. The only record kind for a home's registration needs a bucket group and a generation of at least 1.
  Fix: Allow a kind-2 record whose registration has `group` `ABSENT` (0xFFFFFFFF) and `generation` 0 for a get-or-create without a member, and change §12.2's check to "`group` below 2¹⁸ with `generation` ≥ 1, or `ABSENT` with `generation` 0". The alternative is to state that a round may carry section-3 dictionary entries with no decision.
- **BL-4** (minor, §12.2 Write-set record, section 5) — skeptic: confirmed: Section 5 holds "the commit record the client attached", but no client body carries one. The section's contents have no wire source, and its length and validity are undefined.
